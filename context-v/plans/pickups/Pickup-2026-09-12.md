## What shipped this session

### The app bug (gh #95) — the original complaint

Three corpora in a row showed the **same three sources**, each under its own name
with its own confident "3 sources" badge.

Ruled out first, both innocent:

- **The data.** Production SurrealDB is clean and correctly scoped — seven
  corpora with counts 3/2/4/1/5/1/1 and distinct `source_uuid`s.
- **The query.** `assembleDomain` filters on
  `(client_slug, domain_type, domain_slug)`, and so does every write path.

The cause was the socket. `workspace-service` logged `ws close` at 20:30:39 and
did not reconnect until 20:58:43; all three clicks landed inside that window.
`select()` sets `activeSlug` synchronously and assigns `sources` *after* an await
that never resolved. Identity moved, content did not, and **nothing could detect
the disagreement** because a list of sources carried no trace of the corpus it
came from.

Fix: `domain.assemble` now echoes the `(type, slug)` it answered for, and the
curator refuses replies that do not match the current selection. That closes the
class rather than the symptom — an out-of-order reply can no longer win either.

**Deliberate softness:** the match is enforced only when the echo is present,
because the resolver and the curator deploy independently. A resolver on the old
build sends no echo, and rejecting that would blank the surface instead of
merely misfilling it. **Tighten to a required echo once both sides are deployed
everywhere** — that is a real follow-up, not a nicety.

### The watchdog (gh #94)

`deploy-watch.yml` had **never once run green**. All 200 retained runs failed,
back to 2026-08-23; the secret was last set 2026-08-15. It had been blind since
roughly the day it was wired.

Three separate defects, each hidden behind the previous one:

1. **The token was malformed** — `raw=70 trimmed=63`, not the 36-char UUID a
   Railway project token is, and rejected as an account token too.
2. **`gh` had no repo to infer.** The job never checks out, so every `gh issue`
   call died on `fatal: not a git repository`. Unreachable while the token was
   broken. Fixed with `GH_REPO` on both gh-using steps.
3. **The cron was fiction.** Measured: **38 scheduled runs delivered against 496
   requested — 8%**, median gap 185 minutes against a requested 15. GitHub drops
   high-frequency schedules under load. The old comment worried about Railway's
   rate limit, which was never the binding constraint.

So detection moved to push (Railway webhook → Vercel relay → `repository_dispatch`)
and the cron was demoted to an hourly reconciler at `:23`.

The design rule is in [[../../blueprints/Webhook-As-Wake-Up-Not-As-Truth]]: **the
relay forwards a wake-up, not a payload.** The woken job re-queries Railway and
reaches its own conclusion. Railway payloads are unsigned, so this is what makes
a forged dispatch harmless — verified by sending a lie, which produced a green
run that opened nothing.

## Watch paths: resolved, and NOT the way it was attempted

**Current state is safe: every push deploys everything, exactly as before this
session touched anything.** Nothing is silently undeployed. Read on only if you
want the doc-commit noise gone.

Two attempts, both measured:

| Patterns | Result |
|---|---|
| `/**` + `!` negations | **Nothing matched.** Every service skipped every commit for ~3 hours, including `802d45c`, which is full of TypeScript. |
| `**` + `!` negations | **Everything matches.** Inclusion works (`802d45c` class of commit builds), but the negations are ignored — a docs-only commit (`70b083f`) still built. |

So `**` matches correctly and **Railway's watch paths do not honour gitignore-style
`!` negation**, whatever the docs' "gitignore-style patterns" phrasing implies.
The current config is therefore equivalent to having no watch paths at all.

**If you want the exclusion, use explicit includes rather than negation** — list
what should trigger a build and let omission do the excluding:

```
apps/**
packages/**
services/**
shell/**
package.json
pnpm-lock.yaml
pnpm-workspace.yaml
Dockerfile
```

That leaves `context-v/`, `changelog/`, and root `*.md` out by omission. A `.md`
inside `apps/**` would still trigger a build; acceptable.

**Two traps, both paid for already:**

1. `get_service_config` accepts `watch_patterns` on write and **does not return
   them on read.** There is no way to confirm the setting from the API — only by
   pushing and observing `SKIPPED` vs `BUILDING`. Budget a real commit per
   attempt.
2. The failure modes are asymmetric. Over-matching costs wasted rebuilds.
   **Under-matching silently stops shipping your code** and looks identical to a
   quiet day. If an attempt skips a code commit, clear the patterns immediately
   rather than iterating on syntax.

Shipping past a skipped deploy, if it happens again:

```bash
railway deployment redeploy --from-source -y -s <service> -e production \
  -p a45c72fa-8d40-464a-ba0d-a0940522de8e
```

## A pattern worth naming

Three instances of one shape turned up in this codebase in three days:

- A curator rendering an **unanswered fetch** as content
- A vitest suite reporting a **throwing import** as "no tests", not a failure —
  which is why `apps/corpora-curator/test/curation.test.ts` sat dead since gh #93
  and nobody noticed eight tests vanish
- A watchdog that would have reported **healthy on an empty read**, had its own
  author not guarded against exactly that

**Absence of signal rendered as positive signal.** The guard already written into
`deploy-watch.yml` says it best: *an empty service list must NEVER read as
healthy.* Worth treating as a review question rather than three incidents.
